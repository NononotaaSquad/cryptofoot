# D5-004: Case model and stable identifier

- **Status:** proposed
- **Date:** 2026-11-21
- **Type:** own proposal; closes the dependency of D26-005
- **Source:** issue #5 criteria ("a Case ... stable identity that Analyses can reference", stored in MongoDB); `backend-architecture.md` ADR-001, ADR-002; D25-002 (`caseId` is a plain reference); D26-005 (port `CaseIdentifierSource` proposed for the E1 owner)
- **Proposed by:** AI agent (Claude)
- **Approved by:** nobody yet

## Problem and context
Analyses (#25), the rerun (#26) and the schedule (#27) refer to a Case by a plain string `caseId`; no Case store existed.

## Options considered
A document per Case with a MongoDB-generated id; a UUID generated by the application; a business key from the identifiers.

## Decision (proposed)
Collection `cases`, one `CaseRecord` per Case: `id` (the MongoDB ObjectId as a string, generated on insert, never changes), the six identifiers (`PersonIdentifiers`) and `createdAt` (UTC, from the application clock). A Case is only inserted here; there is no update or delete. No deduplication: the same data creates two independent Cases (no business rule asks for merging or uniqueness). `CaseService` also implements `CaseIdentifierSource`: it returns the identifiers of a Case (including the full name) as input for an Analysis, or nothing for an unknown id.

## Consequences and risks
- Other modules can now resolve a Case; nothing wires it into the Analysis flow yet (`AnalysisRerunService` is still not a bean).
- Analyses created before this change refer to ids that are not Cases; they are not validated.
- Personal data is stored in plain form in MongoDB (no retention or deletion rules).
- Listing and reading a Case (`listCases`, `getCase`) remain E6 stubs.

## Verification
`CaseCreationSpec` (id and data saved, two equal inputs give two Cases, `currentIdentifiers`).
